# МИРЭА через reverse SSH SOCKS5-прокси (обход гео-блока)

## Зачем это нужно

Сервер бота физически за пределами РФ (напр. GCP, США). Сайт МИРЭА
(`priem.mirea.ru`) стоит за DDoS-Guard, который **режет не-российские IP по
гео** → на любые запросы к МИРЭА приходит `403` со страницей блокировки. При
этом четыре других вуза (МЭИ, ФинУ, СТАНКИН, Московский политех) с того же IP
отвечают `200` — блок
точечный, именно у МИРЭА.

Решение: запросы **только к МИРЭА** пустить через **домашний интернет** с
российским IP (он до МИРЭА достукивается). Механизм — SSH-туннель с
SOCKS5-прокси:

```
бот на сервере (не-RU) ──запрос к МИРЭА──▶ SOCKS5 на сервере 127.0.0.1:1080
                                                  │  (SSH-туннель)
                                                  ▼
                                        домашний ПК (RU) ──▶ priem.mirea.ru ✅
```

Домашний ПК **сам** инициирует исходящее SSH-соединение к серверу, поэтому на
домашнем роутере ничего пробрасывать не нужно.

Остальные вузы (МЭИ, ФинУ, СТАНКИН, Московский политех) прокси не используют —
идут напрямую. Оговорка про Политех: он добавлен позже этой инструкции, и с
зарубежного IP его никто не проверял — если он вдруг тоже окажется под
гео-блоком, симптом будет тот же (403 или пустой ответ на все направления).

## Как это поддержано в коде

- `src/robot/mirea_pool.py` читает адрес прокси из переменной окружения
  `MIREA_PROXY` (напр. `socks5h://127.0.0.1:1080`) и прокидывает его в оба
  запроса к МИРЭА. Переменная не задана → прямой доступ (локально с RU-IP всё
  работает и так).
- `requirements.txt` содержит `pysocks` (нужен `requests` для схемы `socks5h`).
- `scripts/docker_deploy.sh` пробрасывает `MIREA_PROXY` в контейнер и, если она
  задана, добавляет `--network host`.
- Отказоустойчивость: при сбое запроса к МИРЭА `build()` откатывается на
  последний кэш (`_load_cache(ignore_ttl=True)`) — офлайн-туннель не роняет
  бота, МИРЭА просто показывает последние известные данные.

## Предпосылки

- SSH-доступ с домашнего ПК на сервер **по ключу** (не по паролю) — туннель
  поднимается автоматически, вводить пароль некому.
- **OpenSSH 7.6+** на домашнем ПК (для reverse-SOCKS `-R 1080`). Проверка:
  `ssh -V`.
- Домашний ПК должен быть **включён**, пока нужен свежий МИРЭА (выключен/спит →
  туннель падает → МИРЭА замирает на кэше, остальные вузы не затронуты).

Ниже `user@cloud-server` — замени на своего SSH-пользователя и адрес сервера.

## Шаг 1. SSH-ключ (если ещё нет)

На домашнем ПК:

```bash
ssh-keygen -t ed25519             # если ключа ещё нет
ssh-copy-id user@cloud-server     # закинуть публичный ключ на сервер
ssh user@cloud-server             # проверить: заходит БЕЗ пароля
```

## Шаг 2. Проверить туннель вручную

На домашнем ПК:

```bash
ssh -N -R 1080 user@cloud-server
```

- `-R 1080` — **reverse dynamic forwarding**: на сервере поднимается SOCKS5 на
  `127.0.0.1:1080`; всё, что туда отправлено, туннелируется на домашний ПК, и
  реальный запрос делает уже он со своего RU-IP.
- `-N` — только туннель, команд не выполнять.

Оставь висеть и перейди к шагу 3.

## Шаг 3. Убедиться, что через туннель МИРЭА пускает

На **сервере** (пока туннель из шага 2 висит):

```bash
# через туннель (домашний RU-IP) — ждём 200:
curl --socks5-hostname 127.0.0.1:1080 -s -o /dev/null -w "%{http_code}\n" \
  https://priem.mirea.ru/competitions_api

# напрямую (IP сервера) — ждём 403:
curl -s -o /dev/null -w "%{http_code}\n" https://priem.mirea.ru/competitions_api
```

`200` через туннель против `403` напрямую = туннель работает.

## Шаг 4. Автоподъём туннеля

Ручной `ssh` умрёт при обрыве связи или перезагрузке. Нужен автоперезапуск —
любой из вариантов на домашнем ПК.

### Вариант A — autossh (проще)

```bash
autossh -M 0 -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
        -o ExitOnForwardFailure=yes -N -R 1080 user@cloud-server
```

### Вариант B — systemd-юнит (надёжнее, стартует при загрузке)

`~/.config/systemd/user/mirea-tunnel.service`:

```ini
[Unit]
Description=Reverse SOCKS tunnel to cloud for MIREA
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/usr/bin/ssh -N -R 1080 \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes \
  user@cloud-server
Restart=always
RestartSec=10

[Install]
WantedBy=default.target
```

```bash
systemctl --user enable --now mirea-tunnel
loginctl enable-linger "$USER"     # чтобы юзер-сервис жил без активного логина
```

Зачем опции:

- `ServerAliveInterval=30` + `ServerAliveCountMax=3` — пинг сервера каждые 30с,
  после 3 пропусков (90с) связь считается мёртвой и рвётся → перезапуск.
- `ExitOnForwardFailure=yes` — если порт 1080 на сервере не поднялся (напр. завис
  старый), ssh сразу выходит → перезапуск. Без этого ssh висел бы «живой», но с
  нерабочим туннелем.

> Домашний ПК на Windows: systemd не подойдёт — через WSL или `autossh` в
> планировщике задач.

## Шаг 5. Запустить бота с прокси (на сервере)

```bash
MIREA_PROXY=socks5h://127.0.0.1:1080 ./scripts/docker_deploy.sh
```

Что и зачем:

- **`socks5h`** (а не `socks5`) — DNS-резолвинг `priem.mirea.ru` тоже уходит на
  домашнюю сторону, а не через (не-RU) DNS сервера.
- **`--network host`** (скрипт добавляет сам, когда `MIREA_PROXY` задан) — туннель
  слушает на `127.0.0.1` **хоста-сервера**. Контейнер со своим сетевым namespace
  имел бы свой `127.0.0.1` и туннель бы не увидел; `--network host` отдаёт
  контейнеру сетевой стек хоста.
- Переменная прокидывается в бота; через прокси идут **только запросы к МИРЭА**.

## Поведение в работе

- Туннель жив → МИРЭА догревается свежими данными каждые ~2ч, как остальные вузы.
- Туннель/домашний ПК офлайн → запрос к МИРЭА падает сразу (`ConnectionRefused`,
  без зависаний) → бот отдаёт **последний кэш МИРЭА**. Три других вуза свежие,
  МИРЭА показывает последнее известное, пока туннель не вернётся.

## Диагностика

| Симптом | Причина / что смотреть |
|---|---|
| `403` даже через туннель | Туннель не поднят / порт 1080 занят / `curl` без `--socks5-hostname` |
| `Connection refused` на 1080 | Туннель не запущен (шаг 2/4) или упал |
| Бот не видит туннель, а `curl` с хоста видит | Контейнер без `--network host` (задай `MIREA_PROXY` при деплое) |
| `InvalidSchema: Missing dependencies for SOCKS` | Не установлен `pysocks` (есть в requirements — пересобери образ) |
| МИРЭА замер на старых данных | Туннель офлайн — бот на fallback-кэше; подними туннель, дождись прогрева |
