# Самообслуживание в Telegram-боте по коду поступающего — дизайн

Дата: 2026-08-01

## Контекст

Сейчас Telegram-бот однопользовательский: доступ дают вручную через
`allowed_chat_ids` в `config/telegram.json`, а личность «кого показываем» —
захардкожена как «Дима» в двух независимых местах:

- `config/robot.json` (`dima.code`/`dima.score`/`dima.consent` +
  `universities.<Вуз>.dima_list_code`/`dima_priorities`) — использует
  команда `/робот` (симулятор каскадного зачисления, реализован сегодня
  для 4 вузов: Финуниверситет, МИРЭА, МЭИ, СТАНКИН).
- `config/programs.json` (поле `dima_score` на каждую запись программы,
  все 10 вузов) — использует команда `/статус` через
  `src/service.py::load_results()`/`refresh_all()` и
  `src/telegram_notify.py::send_status()`. Отдельно тем же
  `load_results()`/`refresh_all()` пользуется Streamlit-дашборд `app.py` —
  он НЕ входит в область этой задачи и не меняется.

Нужно: убрать ручной допуск по `chat_id`, вместо этого — самостоятельная
регистрация любым пользователем по его уникальному коду поступающего
(единый код на все вузы, куда он подавался — подтверждено на примере
Димы: одно и то же значение `dima_list_code` стоит во всех блоках
`config/robot.json`). После регистрации `/статус` показывает КАЖДОМУ
пользователю его собственные данные по 4 вузам с готовой инфраструктурой
полного пула (не 10 — расширение на оставшиеся вузы отдельная задача на
будущее).

## Цель

- Убрать проверку `allowed_chat_ids` — бот отвечает любому.
- Самостоятельная регистрация: незнакомый `chat_id` → бот просит код →
  следующее сообщение с числом сохраняется как код пользователя.
- `/статус` — переопределяется на новую логику: для зарегистрированного
  пользователя проходит по 4 вузам с полным пулом (МИРЭА, МЭИ, СТАНКИН,
  Финуниверситет), для каждого — если код найден в живом пуле, показывает
  проходит/не проходит по отслеживаемым направлениям, с реальным баллом
  из пула и реальным поданным порядком приоритетов (без ручного ввода).
- `/робот <вуз>` — тот же движок симуляции, что и сейчас, но личность
  («кого симулируем») берётся из кода зарегистрированного пользователя, а
  не из `config/robot.json`. Формат вывода не меняется.
- `/приоритет <вуз>` — остаётся (уже реализован, менять UX не нужно), но
  сохраняет override в новое персональное хранилище вместо
  `config/robot.json`. Не обязателен — без него используется реальный
  поданный порядок.
- `/обновить` — без изменений в доступе, открыт всем как и остальные
  команды после этой задачи.
- Старая механика `/статус` (баллы по `dima_score`, все 10 вузов,
  `load_results`/`send_status`) — закомментировать в
  `scripts/telegram_bot.py` (не удалять, оставить для возможного
  возврата), заменить на новую. `src/service.py`, `app.py`,
  `scheduler.py`, `update.py`, `config/programs.json` — НЕ трогать, они
  вне области (Streamlit-дашборд продолжает работать как есть на всех 10
  вузах).
- `config/robot.json` — блок `dima` и поля `dima_list_code`/
  `dima_priorities` по вузам становятся не нужны (заменяются персональным
  хранилищем). Оставить файл рабочим (не ломать `load_robot_config()`),
  но новые персональные данные туда не пишутся.

## Область изменений

- Новый файл `src/telegram_users.py` — хранилище «chat_id → код +
  приоритеты по вузам» (`data/telegram_users.json`, в `.gitignore`).
- `src/telegram_config.py` — убрать `allowed_chat_ids` из проверки доступа
  (поле можно оставить в датаклассе для обратной совместимости чтения
  файла, но `is_allowed()`/сам гейт — убрать из использования).
- `src/telegram_notify.py` — убрать/не использовать `is_allowed()` в
  боте (см. ниже, где именно).
- `scripts/telegram_bot.py`:
  - убрать вызов `is_allowed(...)` перед диспетчеризацией команд;
  - добавить обработку «незнакомый chat_id → жду код» перед диспетчеризацией
    команд (кроме `/start`/`/help`, которые по-прежнему работают всегда);
  - переписать блок `/статус` на новую логику (см. ниже);
  - изменить блок `/робот` и `/приоритет`, чтобы личность/приоритеты брались
    из `src/telegram_users.py` вместо `config/robot.json`;
  - старый код `/статус` не удалять — закомментировать блоком с пояснением.
- `src/robot/simulator.py`, `src/robot/direction_keys.py`,
  `src/robot/*_pool.py` — **не меняются**. Симулятор уже принимает
  `RobotSettings`/`university_cfg` как параметры, не константы — новая
  логика просто конструирует их на лету для каждого запроса вместо чтения
  `config/robot.json`.
- `src/robot/priorities.py` — `get_saved_priority_ids`/`save_priority_ids`
  сейчас читают/пишут `config/robot.json`. Нужны аналоги, работающие через
  `src/telegram_users.py` (по `chat_id` + вузу), либо параметризовать
  существующие функции источником хранения — на усмотрение этапа
  реализации, с сохранением текущих сигнатур там, где это возможно, чтобы
  не трогать `src/robot/telegram_priorities.py`/UI редактора приоритетов
  без необходимости.

## Хранилище пользователей

`data/telegram_users.json` (новый файл, добавить в `.gitignore` рядом с
`config/telegram.json`):

```json
{
  "1494256272": {
    "code": "1824102",
    "priorities": {
      "МИРЭА": [48, 16, 28, 20, 24, 8, 46, 10, 12, 17, 50, 53, 41]
    }
  }
}
```

- Ключ — `chat_id` (строка, т.к. ключи JSON всегда строки).
- `code` — обязателен после регистрации, единый на все вузы.
- `priorities` — опциональный словарь `вуз → [id, id, ...]`, заполняется
  только если пользователь явно вызывал `/приоритет`. Отсутствие ключа для
  вуза = использовать реальный поданный порядок из пула (никакого
  дефолтного списка городить не нужно — `run_robot_simulation(...,
  priority_ids=None)` уже обрабатывает это корректно через существующую
  `_resolve_dima_person`).

## Механика: как /статус и /робот определяют личность без config/robot.json

`run_robot_simulation(university, settings, *, use_cache, priority_ids)`
принимает `settings: RobotSettings` как параметр — датакласс с полями
`dima_code, dima_score, dima_consent, require_consent, universities: dict`.
Ничего в `simulator.py` не привязано к чтению `config/robot.json`
напрямую — этим занимается только `load_robot_config()` в
`src/robot/config.py`, которую бот сейчас вызывает как
`settings = settings or load_robot_config()`.

Новая логика в `telegram_bot.py` вместо `load_robot_config()` строит
`RobotSettings` на лету из данных зарегистрированного пользователя:

```python
def _settings_for_user(code: str, university: str, priority_ids: list[int] | None) -> RobotSettings:
    return RobotSettings(
        dima_code=code,
        dima_score=0,
        dima_consent=True,
        require_consent=True,
        universities={
            university: {
                "enabled": True,
                "dima_list_code": code,
            }
        },
    )
```

`dima_score`/`dima_consent` в этом объекте не влияют на результат, когда
код реально найден в пуле — `_resolve_dima_person()` в этом случае берёт
настоящий балл из пула (`found.score`), а `dima_score=0` — только
безопасный дефолт на случай (маловероятный, но существующий как ветка
кода) синтетического участника, если код не найден. `dima_priorities` в
словаре `universities[...]` намеренно не ставится — вместо этого
`priority_ids` передаётся отдельным аргументом в `run_robot_simulation`
(она уже это поддерживает: `priority_ids: list[int] | None = None`),
беря значение либо из персонального оверрайда пользователя, либо `None`.

Это учитывает главный инвариант всего сегодняшнего плана
(`RobotProgram.key`/`ProgramChoice.program_key == str(program.id)`) — он
не зависит от источника `RobotSettings`, только от `direction_keys.py` и
самих пулов, которые не меняются.

## `/статус`: новое поведение

Для зарегистрированного пользователя (`code` есть в
`data/telegram_users.json`):

1. Для каждого из 4 вузов (`Финансовый университет`, `МИРЭА`, `МЭИ`,
   `СТАНКИН`) вызвать `run_robot_simulation(university, settings=..., use_cache=True, priority_ids=...)`.
2. Если `result.error` — код не найден в этом вузе (обычная ситуация,
   человек мог туда не подавать) — пропустить вуз молча или одной строкой
   «не найден», не как ошибку.
3. Если найден — короткая сводка: вуз, зачислен/не зачислен, по какому
   отслеживаемому направлению, приоритет.
4. Если ни в одном вузе не найден — явное сообщение с объяснением
   (проверьте код, либо он подавал не в эти 4 вуза).

Для незарегистрированного — как и раньше, просьба прислать код (см. ниже).

## Регистрация: детали

- `/start`/`/help` работают всегда, без проверки регистрации (как сейчас).
- Любое ДРУГОЕ сообщение от `chat_id`, которого нет в
  `data/telegram_users.json` — если текст похож на код (только цифры,
  разумная длина, например 4–15 символов) — сохранить как `code`, ответить
  подтверждением. Если не похож на код — попросить прислать именно код
  (не пытаться угадывать команды до регистрации).
- Валидация кода при регистрации живым запросом не делается (это было бы
  небыстро при холодном кэше) — просто сохраняется, а на первом `/статус`
  станет ясно, найден он хоть где-то или нет.
- Команда для повторной регистрации/смены кода — например `/код <номер>`
  (переписывает `code` в хранилище) — полезно, если пользователь ошибся
  при первом вводе.

## Обработка ошибок

Как и везде в этом проекте — без падений наружу. Ошибка живого фетча для
одного вуза не должна прерывать проверку остальных трёх в `/статус` (цикл
по вузам оборачивает каждый вызов `run_robot_simulation` независимо — она
и так возвращает `result.error`, а не бросает исключение, так что
достаточно просто проверять `result.error` в цикле, не оборачивая в
`try/except` дополнительно).

## Проверка

В проекте нет pytest — как и весь сегодняшний план, проверяется вживую:
регистрация тестовым `chat_id`, `/статус`/`/робот` реальным зарегистрированным
кодом (например, Диминым — `1824102`), сверка с уже известным по сегодняшним
живым прогонам результатом (МИРЭА: приоритет 12/13, МЭИ: приоритет 2/5,
СТАНКИН: приоритет 1/5).

## Известные ограничения (осознанные, не блокеры)

- Только 4 из 10 вузов — остальные 6 не имеют инфраструктуры полного пула,
  расширение на них не входит в эту задачу (отдельный, сравнимый по объёму
  план на будущее).
- `/обновить` открыт всем без ограничения по частоте — теоретический риск
  злоупотребления живыми запросами к сайтам вузов; осознанно принято
  пользователем, не блокер этой задачи.
- Валидация кода при регистрации не выполняется заранее (см. выше) — если
  пользователь опечатался, узнает об этом только при `/статус`, не сразу.
