# Починка STANKIN_PROGRAMS: id44/id61 тянули не тот конкурсный список — дизайн

Дата: 2026-08-02

Задача в beads: `priem-monitor-vr9` (discovered-from `priem-monitor-v0j`).

## Контекст

При сверке бюджетных мест СТАНКИНа (`priem-monitor-v0j`) обнаружился отдельный
баг, не связанный с числами мест напрямую: `_resolve_program()` в
`src/parsers/remaining.py::StankinParser` — единственная функция, которой
пользуются **и обычный дашборд/бот** (`StankinParser.fetch()`, строка 88,
формирует `PROPERTY_394` для запроса к `gridspisokpostupayushchikh`), **и
робот-пул** (`stankin_pool.py::_tracked_direction_groups()`, строка 225,
вызывает тот же метод для группировки отслеживаемых программ по каталогу).

Словарь `STANKIN_PROGRAMS` (строки 76-83) содержит две пары ключей, которые
должны различать «обычный профиль направления» и «профиль ТОП ИТ» (партнёрская
программа с индустрией — Ростелеком для 09.03.01, «1С» для 09.03.02), но по
ошибке ОБА ключа в каждой паре ведут на одно и то же значение (значение
ТОП-ИТ-профиля):

```python
"разработка программных комплексов в рамках": "09.03.01.01 Разработка программных комплексов",  # id44 — должно вести на "09.03.01 ..."
"разработка программных комплексов": "09.03.01.01 Разработка программных комплексов",             # id47 — верно
...
"цифровые системы управления": "09.03.02.01 Разработка и внедрение корпоративных информационных систем",  # id61 — должно вести на "09.03.02 ..."
"разработка и внедрение корпоративных": "09.03.02.01 Разработка и внедрение корпоративных информационных систем",  # id62 — верно
```

## Подтверждение бага (не гипотеза — проверено эмпирически)

1. **Официальные страницы СТАНКИНа** (`priem.stankin.ru/bakalavriatispetsialitet/{training_programs,osobkvota,otdkvota,tselevayakvota}/`)
   независимо, тремя разными разделами (особая/отдельная/целевая квота),
   перечисляют «информатика и вычислительная техника» (общий профиль,
   id44) и «РАЗРАБОТКА ПРОГРАММНЫХ КОМПЛЕКСОВ» (ТОП ИТ, id47) как ДВЕ разные
   строки с разными числами — не один профиль под двумя именами. То же для
   «Информационные системы и технологии» (id61) vs «РАЗРАБОТКА И ВНЕДРЕНИЕ
   КОРПОРАТИВНЫХ ИНФОРМАЦИОННЫХ СИСТЕМ» (id62).
2. **Живой запрос** к `gridspisokpostupayushchikh` с `PROPERTY_394` = двум
   разным именам направления вернул РАЗНЫЕ наборы кодов абитуриентов (не
   идентичные списки).
3. **`_resolve_program()`, вызванный напрямую** на реальных `ProgramConfig`
   id44/id47/id61/id62 — оба id в каждой паре сегодня возвращают ОДНУ и ту же
   строку (фактически подтверждённый баг на текущем коде, не домысел).
4. **Инфраструктура каталога уже готова**: `FALLBACK_CATALOG`
   (`stankin_pool.py:39-59`) уже содержит обе записи направления отдельно
   («09.03.01 ...» и «09.03.01.01 ...», «09.03.02 ...» и «09.03.02.01 ...») —
   значит скрейпинг каждого списка по отдельности уже работает, чинить нужно
   только резолвинг имени, не инфраструктуру фетча.

## Реальные места общего конкурса для общих профилей (проверено трижды независимо)

| Направление (общий профиль) | Всего КЦП | Особая | Отдельная | Целевая | Основные |
|---|---|---|---|---|---|
| 09.03.01 Информатика и вычислительная техника | 70 | 7 | 7 | 11 | **45** |
| 09.03.02 Информационные системы и технологии | 78 | 8 | 8 | 9 | **53** |

Совпадает с уже стоявшими в config значениями id44=45 и id61=53 — эти два
config-числа были верны с самого начала, ошибка была только в резолвинге
направления, из-за которой робот их игнорировал (склеивал с id47/id62 и
считал по чужой квоте).

## Решение

Точечная правка `STANKIN_PROGRAMS` (2 строки) + добавление 2 новых записей в
`STANKIN_KCP_OVERRIDES` (введён сегодня в `priem-monitor-q1d`/`v0j`):

1. `STANKIN_PROGRAMS["разработка программных комплексов в рамках"]` →
   `"09.03.01 Информатика и вычислительная техника"` (было ошибочно
   `"09.03.01.01 ..."`).
2. `STANKIN_PROGRAMS["цифровые системы управления"]` →
   `"09.03.02 Информационные системы и технологии"` (было ошибочно
   `"09.03.02.01 ..."`).
3. `STANKIN_KCP_OVERRIDES` — добавить:
   `"09.03.01 Информатика и вычислительная техника": 45`,
   `"09.03.02 Информационные системы и технологии": 53`.
   Существующие записи для `.01`-версий (19, 40) не трогать — теперь корректно
   принадлежат только id47/id62 (больше не делят группу с id44/id61).

Это чинит **оба** потребителя `_resolve_program()` одним изменением, так как
и дашборд, и робот читают один и тот же метод. Fallback по `direction_code`
(строки 133-138: `if code == "36959": return "09.03.01.01 ..."`) не трогаем —
он не участвует, пока ключевой матчинг по тексту программы срабатывает первым
(что верно для всех текущих tracked-программ); это резервная ветка на случай,
если текст программы не совпадёт ни с одним ключом словаря.

## Побочный эффект (ожидаемый, не баг)

Warning про «смёрженную пару» (`stankin_pool.py:309-319`, срабатывает при
`len(configs) > 1`) для этих двух направлений перестанет печататься — они
были смёрженной парой только из-за бага резолвинга, реально это два разных
самостоятельных конкурса с раздельными списками и квотами. После фикса
`_tracked_direction_groups()` вернёт для обоих направлений группы из одного
элемента, как для остальных отслеживаемых направлений СТАНКИНа.

## Область изменений

- `src/parsers/remaining.py` — `StankinParser.STANKIN_PROGRAMS`, 2 значения.
- `src/robot/stankin_pool.py` — `STANKIN_KCP_OVERRIDES`, +2 записи.

Не трогаем: инфраструктуру каталога/фетча (уже корректна), `_resolve_program`
как метод (только данные словаря), fallback по `direction_code`, config
СТАНКИНа (числа 45/53 там уже верны), остальные направления.

## Проверка

Автотестов нет — вживую:
1. `parser._resolve_program(...)` для id44/id47/id61/id62 — id44 и id47
   должны вернуть РАЗНЫЕ строки (аналогично id61/id62).
2. Живой запрос `StankinParser().fetch(program)` для id44 и id47 —
   применяемые списки абитуриентов должны различаться (не идентичный набор
   кодов).
3. Полная сборка `StankinFullPool().build(use_cache=False)` — `budget_places`
   для id44=45, id47=19 (без изменений), id61=53, id62=40 (без изменений); ни
   одна пара направлений СТАНКИНа не помечена как «смёрженная» в выводе.
