# Динамические специальности и приоритеты под код пользователя — дизайн

**Дата:** 2026-08-06
**Статус:** согласован, готов к планированию
**Отменяет часть:** `2026-08-06-user-code-validation-design.md` (см. раздел
«Отношение к спеке валидации кода»)

## Цель

Сейчас робот считает по фиксированному списку специальностей из
`config/programs.json` — это Димины направления, зашитые в конфиг. Пользователь
с другим кодом получает прогноз по чужому списку.

Надо: код введён → специальности, их места, проходные баллы и личный порядок
приоритетов подтягиваются **из конкурсных списков под этот конкретный код**.
У кого-то в МИРЭА всплывёт биологическая специальность — покажем её, с её
живыми местами и её проходным.

## Главное: механика уже работает

Это не постройка с нуля. Каскад **никогда** не опирался на список из конфига:
`_try_place` рассаживает людей по `ordered_program_keys()` — по всем их выборам.
Конфиг использовался ровно в одном месте — чтобы **урезать выборы самого
пользователя** до Диминых специальностей (`_filter_choices_to_tracked`).

Доказательство — тот самый fallback, который спека валидации называет багом.
Для кода `1616947` (МИРЭА, ни одной Диминой специальности) фильтр отдаёт все
выборы человека, и робот считает по ним совершенно корректно:

```
  1. Разработка защищенного ПО (10.05.01 Компьютерная безопасность):
       осталось 11/11 (занято 0) ✅ · сайт: проходной 286 ✅
  4. Геоинформационные системы и комплексы (05.03.03 Картография):
       осталось 27/27 (занято 0) ✅ · сайт: проходной 240 ✅
  5. Медицинская физика (03.03.02 Физика): … ✅
```

Живые места, живые проходные баллы, оракул сходится. То есть у нас уже есть
работающий прототип динамики — он просто спрятан в аварийной ветке.

**Следствие:** основная работа не в расчёте, а в отображении и в командах,
которые до сих пор адресуют направления числовым кодом из конфига.

## Данных хватает — проверено

Покрытие по всем направлениям пулов, не только по отслеживаемым (замер
2026-08-06 на живых кэшах):

| вуз | направлений | места живьём | проходной сайта |
|---|---|---|---|
| МИРЭА | 84 | 84 (100%) | 84 |
| МЭИ | 27 | 27 (100%) | 27 |
| СТАНКИН | 21 | 21 (100%) | 21 |
| Финансовый университет | 45 | 40 (89%) | 40 |
| Московский политех | 65 | 65 (100%) | 65 |

Пять исключений ФА — филиальные программы, которых нет в московской очной
секции приказа о КЦП. Проверено: **у всех пяти ноль абитуриентов**, попасть на
них человек не может. Правило на всякий случай всё равно нужно: направление с
`passing_cutoff is None` даёт статус сверки `unavailable`, а не `mismatch`.

Объём на человека: медиана 5–6 направлений, среднее 4.8–7.9, максимум 35
(МИРЭА). Список человеческого размера, резать не нужно.

Платные конкурсы в пулы не попадают (МИРЭА отсекает `compTypeId=6`, Политех —
фильтром `eduFin`), так что «все специальности пользователя» здесь означает
именно бюджетные. Это ровно то, что нужно.

## Что меняется

### 1. Специальности = выборы человека из пула

`simulator._filter_choices_to_tracked` удаляется целиком. Найденный по коду
человек идёт в каскад со своими настоящими выборами и своим настоящим порядком
приоритетов.

### 2. Новый идентификатор направления для команд

`/конкуренты <вуз> <код>` сейчас адресует направление числом `tracked_id` из
конфига. Оно есть далеко не у всех: МИРЭА 13 из 84, МЭИ 5 из 27, СТАНКИН 7 из
21, ФА 4 из 45. А ключи пулов разнородны и для человека непригодны:

| вуз | ключ направления |
|---|---|
| МИРЭА | `1862638921682263350` (19-значный comp_id) |
| МЭИ | `22` либо `entrants_list533.html` |
| СТАНКИН | `44` либо строка направления |
| ФА | `Бизнес-информатика, Бакалавр, Цифровая трансформация…, Очная` |
| Политех | `26` либо `spec_code` |

Вводим **порядковый номер приоритета пользователя** (1..N) — то самое число,
которое и так печатается слева в списке. `/конкуренты МЭИ 3` = «третий мой
приоритет». Номер осмыслен для человека, стабилен, пока он не переподал
документы, и не требует ничего из конфига.

`format_competitors` принимает этот номер, а не `tracked_id`. Текст подсказки
(«код см. в /робот») правится соответственно.

### 3. Код ОКСО в выводе — из пула, а не из конфига

`format._okso_by_tracked_id()` строит словарь по `config/programs.json` и потому
работает только для отслеживаемых. Заголовки пулов код уже содержат:

- МИРЭА, МЭИ — в хвосте: `Анализ данных (01.03.04 Прикладная математика)`
- СТАНКИН — в начале: `09.03.01 Информатика и вычислительная техника`
- Политех — в шапке списка: `09.03.01.07`
- ФА — **кода в заголовке нет**: `Бизнес-информатика, Бакалавр, …, Очная`

Добавляем поле `RobotProgram.okso_code: str | None`, каждый пул заполняет его
там, где знает. У ФА — `None`, и направление показывается без кода. Это честнее,
чем подставлять код по нечёткому совпадению названий.

### 4. Редактор приоритетов листает реальные направления

`src/robot/telegram_priorities.py` сейчас перечисляет программы из конфига.
Должен перечислять направления пользователя из пула, в его настоящем порядке по
умолчанию, и позволять переставлять только их.

### 5. Сохранённый порядок хранит ключи, а не id конфига

`get_saved_priority_ids` / `save_priority_ids` работают с `program_id` из
`config/programs.json`. Переходят на ключи направлений пула
(`RobotProgram.key`).

Миграция: старые сохранённые id **сбрасываются**, не конвертируются.
Основание — сохранённый порядок есть только у одного чата (Димин), а порядок по
умолчанию теперь и так берётся настоящий, с сайта. Писать конвертер ради одной
записи, которая и без него станет верной, незачем.

`_apply_priority_order` продолжает только **переупорядочивать** реальные
направления: `require_in_pool=True`, как требует спека валидации. Приписать
направление, куда человек не подавал, нельзя ни при каком сохранённом порядке.

### 6. Сверка считается по направлениям пользователя

`result.tracked_programs` по смыслу перестаёт быть «отслеживаемыми» и
становится «направлениями пользователя» — переименовать в `user_programs`,
заполнять по его выборам, а не по `tracked_id is not None`.

`verification.build_verification_report` сверяет места и прогноз по этому же
набору. `PLACEMENT_VERIFIED_UNIVERSITIES` остаётся как есть: оракул зависит от
вуза, а не от того, чьи специальности смотрим.

### 7. `config/programs.json` остаётся, но робот на него не опирается

Конфиг продолжает питать старый трекер позиций (`src/parsers/`) и словарь
ОКСО-кодов `direction_keys.OKSO_CODES`. Робот из него больше не берёт ни список
специальностей, ни порядок приоритетов, ни места.

`tracked_id` в `RobotProgram` сохраняем: он безвреден, помогает при отладке
и связывает пул со старым трекером.

## Отношение к спеке валидации кода

Спека `2026-08-06-user-code-validation-design.md` требует отвергать код, который
не участвует **ни в одной из отслеживаемых специальностей**. С динамическими
специальностями понятие «отслеживаемая специальность» исчезает: специальности у
каждого свои.

Правило валидации поэтому упрощается и остаётся содержательным:

| было (спека 2) | стало (эта спека) |
|---|---|
| код есть хотя бы на одной отслеживаемой спец | код найден хотя бы в одном пуле |
| `NOT_IN_TRACKED_ERROR` — есть в вузе, но не на наших спец | **не нужен**, случая больше не существует |
| «не участвует в отслеживаемых специальностях» | «не участвует в этом вузе» |

Что из спеки 2 остаётся в силе без изменений:

- сама проверка при регистрации, только по кэшу, без сети (~0.6 c на пять вузов);
- отказ только по полным основаниям (все пулы прочитаны, нигде не нашлось);
- `require_in_pool=True` — сохранённый порядок не дописывает направления;
- `/статус` называет все вузы поимённо, включая те, где человека нет.

Что из спеки 2 отменяется:

- удаление fallback в `_filter_choices_to_tracked` — сам метод исчезает целиком;
- константа `NOT_IN_TRACKED_ERROR` и её ветка в `_format_error_response`;
- различение «нет в вузе» и «есть, но не на наших спец» в тексте отказа.

Порядок реализации поэтому важен: **спека 3 идёт первой или одновременно со
спекой 2**, иначе часть работы спеки 2 придётся тут же снести.

## Границы

- Только бюджетные конкурсы — платные в пулы не попадают by design.
- Только те вузы, где человек реально есть; остальные показываются строкой
  «не участвуете».
- Уровень обучения и форма — как настроено в пулах (бакалавриат/специалитет,
  очная). Магистратуру и заочную динамика не открывает.
- Человек с 35 направлениями получит длинный ответ; `send_long_message` это уже
  умеет, искусственный предел не вводим.

   09.03.01.02, 01.03.02, 09.03.01.06, 09.03.01.04`.

   пользователя.
5. ОКСО-код печатается у МИРЭА, МЭИ, СТАНКИНа, Политеха; у ФА направление

6. Редактор `/приоритет` предлагает переставить реальные направления
   пользователя, а не Димины.
7. Сохранённый порядок применяется, но добавить чужое направление им нельзя.
8. Сверка мест и прогноза считается по направлениям пользователя; направление
   без проходного даёт `unavailable`, а не `mismatch`.
9. Прогон по всем пяти вузам для кода `1824102` — ни одного исключения, времена
   ответа не выросли (данные те же, фильтр только снят).
