# Валидация кода пользователя и показ только реальных специальностей — дизайн

**Дата:** 2026-08-06
**Статус:** согласован, готов к планированию

## Цель

Две связанные правки поведения бота:

1. При регистрации **форсировать актуальный код** — такой, который реально
   участвует в бюджетном конкурсе хотя бы на одной из отслеживаемых
   специальностей. Сейчас принимается любая последовательность цифр.
2. Показывать человеку **только те специальности, где он действительно есть**,
   а про вузы, где его нет, говорить прямо: не участвуете.

## Что происходит сейчас (замерено на живых кэшах 2026-08-06)

### Код не проверяется вообще

`src/telegram_users.py::looks_like_code` — единственная проверка, регулярка
`^\d{4,15}$`. Дальше `set_user_code` сохраняет что угодно.

### Половина людей в пуле — не на наших специальностях

| вуз | всего в пуле | без отслеживаемых спец |
|---|---|---|
| МИРЭА | 25605 | 13216 (52%) |
| МЭИ | 18453 | 9948 (54%) |
| СТАНКИН | 8170 | 3500 (43%) |
| Финансовый университет | 16749 | 12901 (77%) |

То есть случай «код есть, но не там» — не редкость, а больше половины.

### Для такого кода робот показывает чужие специальности

`simulator._filter_choices_to_tracked` при пустом пересечении возвращает
**все** выборы человека, включая неотслеживаемые. Проверено на коде `1616947`
(МИРЭА):

```
Учитываются приоритеты (5):
  1. Разработка защищенного ПО (10.05.01 Компьютерная безопасность) …
  4. Геоинформационные системы и комплексы (05.03.03 Картография) …
  5. Медицинская физика (03.03.02 Физика) …
```

Ни одной нашей специальности. Робот работает вхолостую и выдаёт уверенный
прогноз по направлениям, которые мы не отслеживаем.

### Частичное участие уже работает верно

Код `1514555` есть в 4 из 5 отслеживаемых спец МЭИ — робот показывает ровно 4.
Это поведение сохраняем.

### Но сохранённые приоритеты его ломают

Тот же код с сохранённым порядком `[7, 22, 23, 35, 45]` даёт **5** строк —
добавляется «Прикладная информатика» (код 23), где человека нет. Причина:
`_apply_priority_order(..., require_in_pool=False)` в `_resolve_dima_person`.

### `/статус` молчит про вузы, где человека нет

Для кода `1514555`:

```
📊 Статус по коду 1514555

— МИРЭА —
✅ Зачислитесь: Фуллстек разработка …

— МЭИ —
✅ Зачислитесь: Фундаментальная информатика …
```

СТАНКИН и ФА не упомянуты вовсе (`if result.error: continue`). Человек не
понимает: он там не участвует или данные не готовы.

## Решение

### A. Проверка кода при регистрации

Новый модуль `src/robot/code_lookup.py`:

```python
@dataclass
class CodePresence:
    tracked: list[str]         # вузы, где код есть на отслеживаемых спец
    untracked_only: list[str]  # код в вузе есть, но только на чужих спец
    absent: list[str]          # пул прочитан, кода нет вовсе
    unchecked: list[str]       # кэш не прочитался — судить не можем

    @property
    def is_valid(self) -> bool:
        return bool(self.tracked)

def find_code_presence(code: str) -> CodePresence: ...
```

Механика: по каждому вузу из `robot_ready_universities()` берём
`read_cached_pool(parser)` — **только кэш, ни одного сетевого запроса**, — ищем
человека по коду и проверяем пересечение его `choices` с
`{direction_key_for_program(p) for p in tracked_programs}`.

**Стоимость** (замерено): МИРЭА 0.23 c, ФА 0.14 c, МЭИ 0.09 c, СТАНКИН 0.05 c —
около 0.5 c на все четыре, с Политехом ~0.6 c. Это разовая проверка при
регистрации, а не на каждую команду; синхронно в цикле `getUpdates` приемлемо.

Поведение при регистрации (`/код <n>` и голое число от незарегистрированного):

| ситуация | действие |
|---|---|
| `tracked` не пуст | сохранить; ответить, где участвует и где нет |
| `tracked` пуст, `unchecked` пуст | **не сохранять**; назвать причину и попросить актуальный код |
| `tracked` пуст, `unchecked` не пуст | сохранить с оговоркой: проверить по таким-то вузам не удалось |

Последняя строка — сознательная уступка. Отвергать код, когда часть кэшей ещё
не собрана (первые минуты после рестарта бота), значило бы запирать снаружи
живого пользователя из-за нашего же прогрева. Отказ только по полным
основаниям: все вузы проверены, ни в одном не нашлось.

Текст отказа должен различать два случая, иначе он вводит в заблуждение:

- код нигде не найден → «Код N не найден в списках ни одного из отслеживаемых
  вузов»;
- код найден, но не на наших специальностях → «Код N есть в списках МИРЭА, но
  не на отслеживаемых специальностях» + перечисление наших направлений.

### B. Только реальные специальности

**B1. Убрать fallback «показать всё».** В `_filter_choices_to_tracked` ветка
«пересечение пусто → вернуть `dima.choices`» удаляется. Вместо неё симуляция
завершается ошибкой с новой константой рядом с `POOL_NOT_READY_ERROR`:

```python
NOT_IN_TRACKED_ERROR = "Ваш код есть в списках вуза, но не на отслеживаемых специальностях"
```

`format._format_error_response` получает ветку под неё — рядом с существующей
«не найден в списках вуза».

**B2. Не добавлять специальности из сохранённого порядка.**
`_resolve_dima_person` вызывает `_apply_priority_order(..., require_in_pool=False)`.
Меняем на `True`, чтобы сохранённый порядок мог только **переупорядочить** то,
что человек реально подал, но не дописать несуществующее.

Осторожно: `require_in_pool=False` стоял там намеренно — комментарий объясняет,
что человека, вычеркнутого пометкой «Зачисляется в другой КГ», всё равно нужно
показать, потому что подавал он туда реально. Разбор показывает, что переход на
`True` это не ломает: такие выборы остаются в `dima.choices` с флагом
`enrolls_elsewhere`, отсекаются они только в `ordered_program_keys`, а
`pool_keys` строится по `dima.choices` целиком. **Но проверить это надо живьём
на МЭИ** — именно оттуда взялся комментарий, и рассуждение тут не заменяет
прогон.

**B3. `/статус` называет все вузы поимённо.** В `_format_multi_status` вместо
молчаливого `continue` — строка на каждый вуз:

| состояние | строка |
|---|---|
| код найден, проходит | как сейчас |
| код найден, не проходит | как сейчас |
| кода нет / только чужие спец | `— Вуз —` + «Вы не участвуете в отслеживаемых специальностях» |
| пул не готов (`POOL_NOT_READY_ERROR`) | `— Вуз —` + «⏳ данные ещё собираются» |
| вуз выключен (`config_error`) | не показывать вовсе |

Существующая сводка «Код не найден ни в одном из N вузов» остаётся: она
срабатывает, когда не нашлось нигде, и подсказывает `/код`.

## Границы

- Проверка идёт **только по кэшу**. Ходить в сеть при регистрации нельзя:
  полная пересборка ФА и СТАНКИНа — по три с половиной минуты, бот на это время
  перестал бы отвечать всем чатам сразу.
- Уже зарегистрированные коды задним числом не перепроверяются: у бота один
  пользователь, а массовая ревалидация чужих сохранённых кодов при старте — не
  та задача, что здесь решается.
- «Отслеживаемые специальности» = программы из `config/programs.json` по вузу с
  соответствующим `parser`. Список меняется правкой конфига, отдельного
  механизма не заводим.

9. При пустых кэшах любой код принимается с оговоркой о непроверенных вузах.
